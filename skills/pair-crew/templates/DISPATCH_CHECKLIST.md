# pair-crew 派发前检查清单（每次派发前过一遍）

## 【必须由用户亲自做】agent 做不到，别假装能

遇到下面任一项，**停下来把话说明白**，不要用变通绕过。

| # | 动作 | 为什么 agent 做不到 | 你要对用户说的话 |
|---|---|---|---|
| 1 | 在 IDE 里**新建项目 / 打开文件夹** | 弹的是**系统原生文件夹对话框**，CDP 只够得着网页 DOM | 「请点『新项目』→ 选 `<绝对路径>`，系统对话框我点不到」 |
| 2 | 授予**完全访问 / 信任文件夹** | 权限弹窗属于用户授权，模拟点击等于绕过授权 | 「请在那个任务里点『完全访问』」 |
| 3 | 点排队消息的**「插话 / 立即」** | 仅在生成中出现，且文案各 IDE 不同（ZCode=`立即`，Qoder=`插话`） | 先跑 `send_followup.py` 自动点；仍卡住再说「请手动点气泡上的插话」 |
| 4 | **Story 需求确认 / 冻结** | 边界和取舍只能人定 | 一次性呈报：现状证据 / 目标 / 有锚点的问题 / 拆分 / 用例 / 风险 |
| 5 | **每次外部派发的确认** | 花额度、占 IDE | 「派给 `<工具>`、项目 `<名>`、路径 `<路径>`、新建任务、只读，确认？」 |
| 6 | 评审超轮次 / 双方**结论对立** | 是裁决不是技术问题 | 并列两份结论 + 分歧点，请用户定 |
| 7 | **合入 main / 对外发布** | 高风险不可撤销 | 「改动 N 个文件，自检通过，要不要合」 |
| 8 | 评审期间改了被审对象 | 上一轮直接作废 | 「我改了文件，上轮作废，需重派」 |

口诀：**系统对话框、权限授予、花钱、不可撤销 —— 都是人的。**

## 必须与用户确认

- [ ] 目标工具（qoder / qoder-cn / workbuddy / zcode / mimo）
- [ ] `--project-name` 与 IDE 工作区名一致
- [ ] `--project-path` 绝对路径正确
- [ ] 新建任务还是续写
- [ ] 任务内容与 SCOPE（是否只读）
- [ ] **文件完全访问是否已授予 / 需要点掉弹窗**

## 【硬性】项目归属按绝对路径核对，不能按名字

- [ ] 派发前跑 `ide_guard.py --ide <zcode|qoder> --path <绝对路径>`
- [ ] 返回 `ok:false` 就**停下来**，先让用户把项目建出来，不要「发进当前会话凑合」
- [ ] 真实事故：目标目录在 ZCode 里根本不存在，`send_zcode.py` 只查「侧栏文本含不含
      项目名」，于是把任务静默发进了当时开着的 `coding_skill` 会话
      （`directory = E:\project_self\coding_skill\.mimocode`），脚本一路打印 `SENT`，
      实际上跟目标项目毫无关系
- [ ] 派发后回读会话真实绑定再收工：
      `ide_guard.py --ide zcode --sessions` / `--ide qoder --sessions`
- [ ] 为什么不能靠名字：Qoder 里可能出现**同名工作区重复登记**（实测「捷安泊数据分析」
      登记了两次，指向同一路径但 id 不同）；ZCode 的 `project_id` 由路径派生，
      非 ASCII 会被丢掉（`D:\projects\海豚屋` 和 `D:\projects\做课` 都变成 `proj_d-projects`）

## 【硬性】派发后冻结被审对象

- [ ] **评审跑起来之后，不要改被审文件**
  - 真实踩过：Qoder CN 读到一半文件从 31KB 变成 42KB，它不得不中断重读，
    前 10 分钟的验证全部作废
  - 要改就等这一轮结论落地，改完**再派一轮**，而不是边改边评
- [ ] 同理，被审对象依赖的测试数据 / 状态文件也不要中途覆盖
  - 真实踩过：mock 自测与真实导入共用同一个 `state.json`，
    一次 mock 跑完把 1248 张表的真实进度清成了 8 张
  - 规矩：mock / 演练必须用**独立状态文件**

## 脚本/环境自检

- [ ] `routing_check.py` 无 ERROR（含 VISION_REQUIRED / IDE_OFFLINE）
- [ ] CDP 端口可发现该 IDE（9222–9235）
- [ ] 该工作区在 IDE 侧已存在（否则先注册，如 Qoder `workspaces` 表）
- [ ] 目标 IDE 无进行中任务（避免抢占）

## 派发后

- [ ] 读回是否包含**真实绝对路径**（否则多半是工作区或权限问题）
- [ ] 核对只读约束是否被遵守（未改文件）
- [ ] 写进 BOARD / HANDOFF（含 `session_id` 与状态 `in_review`）

## 【硬性】收工前必须收口

- [ ] 这次派出去的每个评审，都拿到明确判定了吗？
- [ ] 没拿到的，是不是用 `collect_review.py --wait --session <id>` **阻塞等**过，
      而不是查一次就断言「它没回我」？
- [ ] 仍有 `in_review` 时，**禁止**说「任务完成」「评审已通过」

## 读回的现实约束

- CDP 只能读**当前活动视图**。派发后界面若被切到别的任务，`document.body.innerText`
  拿到的是另一个任务的正文，**看起来像「没在跑」其实是跑在后台**
- **所以不要靠抓页面判断状态**，直接读 IDE 数据库：
  - Qoder：`main.sqlite` 的 `chat_session_messages`（`payload_json.parts`）
  - ZCode：`~/.zcode/cli/db/db.sqlite` 的 `message` / `part` 表
  - 现成工具：`collect_review.py`
- 读库**绝对不能加 `immutable=1`**：那是「库不会变」的承诺，SQLite 会跳过 WAL，
  只给打开时的快照 → 新消息永远读不到（实测：真实 44 条，读到 14 条）
- 消息**条数不变 ≠ 没有新结论**：Qoder 在同一条 assistant 消息上原地改写，
  要看最后一条的 `updated_at` 和正文

## 【硬性】续写消息后必须确认没在排队

- 对方**正在生成**时，`insertText + Enter` 进去的消息不会立即执行，而是进排队队列，
  气泡上会多出一个按钮
- **不点它 = 消息永远排在队尾**，表现为「发了没反应」，而你以为它已经收到了
- **按钮文案不固定，各 IDE 不一样**：
  - ZCode：`立即`
  - **Qoder CN：`插话`**
  只认「立即」的脚本在 Qoder 上永远点不到。`send_followup.py` 的 `QUEUE_WORDS`
  覆盖 `立即 / 插话 / 立即发送 / 立即执行 / 打断 / 现在就发`，且取 **y 最大**
  （最靠下 = 最新一条）那个，避免误点历史残留按钮。
- 真实踩过：给 ZCode 和 Qoder 各发一条「立刻出结论」的收尾指令，
  Qoder 那条一直排在队里（因为脚本在找「立即」），白等十分钟。
- 另：续写前用 `--switch-to <会话标题>` 或 `--expect <标题关键词>` 确认发对了会话；
  `send_followup.py` 会在发送前后比对 `chat id`，变了直接报错。

## 权限说明

| IDE | 完全访问 | 自动化现状 |
|---|---|---|
| WorkBuddy | 「允许完全访问」按钮 | `review_dispatch` 可点；失败则人工；新工作区需重启后可搜 |
| Qoder CN / 国际版 | 任务内文件访问确认 | **当前多靠人工点**；工作区可写 `main.sqlite` workspaces 表后 reload UI |
| ZCode | 「完全访问」开关 + 信任文件夹 | 项目创建含原生文件夹框，建议**人工建一次项目**；发消息可用 `send_zcode.py` |
| MiMo IDE | 项目已加入则较顺 | 待实践 |
